# Codex operator instructions for this portable harness

Read docs/portable/windows/QUICKSTART.md and docs/portable/windows/SETUP_WSL.md. For the four-workflow matrix, invoke `python3 -m spineharness.framework_matrix` inside WSL2 Ubuntu as docs/MATRIX_QUICKSTART.md directs; `Run-Harness.ps1` covers the historical two-arm Jira path. All harness Python and model processes must run in the same WSL2 Ubuntu distribution. Keep tools and virtual environments on the Linux filesystem. Use WSL paths in configuration and save result files alongside the Windows package. Run doctor and verify before model work; confinement failures must stop execution. Never disable the sandbox. Native Windows Python and WSL1 are unsupported. This directory is a Windows package with a WSL2 Ubuntu runtime, not the application under test.

1. Obtain the repository path, frozen baseline, Jira site and full issue keys from the user. Inspect the application's documented test setup. Ask only for missing information; do authorized setup yourself.
2. Use connected read-only Jira tools to retrieve the requested issue requirements (summary, description, status, type, updated timestamp, optional criteria). Save supported JSON snapshots under `inputs/`. Never load or print API/Jira secrets. Never write Jira, push, open PRs or alter the original application checkout.
3. Create `benchmark.json` from the example. Use a fresh name, meaningful offline `checks`, correct dependencies, and any selected acceptance suite. Resolve prerequisites equally before measurement. The application must be Python; don't claim support for other runtimes.
4. Use `python3 -m spineharness.portable_benchmark doctor`, `bootstrap`, and `login`. Sign-in is performed by the user with their own account. Tool dependency downloads and the model connection need network; application checks use Linux bubblewrap offline. Request normal execution permissions as needed. Do not disable the project sandbox.
5. Run `prepare` and inspect BASELINE_CHECKS.json, the frozen Jira requirements and the resolved baseline. No model measurement starts here. Check that the issue is neither already solved nor missing prerequisites. If preparation fails, preserve the evidence and diagnose rather than enabling a broken baseline.
6. Run `python3 -m spineharness.portable_benchmark run --approved` when baseline review and data-transfer authorization are already provided. The quick-start prompt supplies that authorization. Do not ask again. Add `--approve-checklist` only if the user has authorized routine checklist continuation. Keep matched model/high settings and 2700-second Spine timeout unless the user changes the protocol.
7. Monitor through completion. Keep the user informed at least every 15 minutes and at failures. Do not treat a successful process exit as proof of correctness. Do not rerun over existing output or automatically start a fresh paid attempt.
8. The run command generates deliverables automatically. `report` regenerates them after closure without model calls. Confirm HTML/Markdown reports, JSON/CSV, usage, patches/plans, manifest, ZIP and checksum exist. Give the user clickable absolute links.
9. Report model usage from closed saved token_usage_record ledgers, deduplicated by response ID, including exported descendants/retries. Missing records are UNKNOWN, never zero. API list-price equivalents are not subscription charges. Keep supervisor tokens separate; if the user's shared calculator exists, run it after the supervision work window closes.
10. Do not manually fix measured application output. Post-audit repair needs a separately measured continuation through native Spine refine with exact feedback, call bound and preserved original output. Label validation after feedback honestly; do not overwrite a first-run failure with its repaired result.

This handover intentionally omits previous Jira issues, results and application patches, as well as credentials, raw conversations, tool environments and the Spine dependency repository. Use the root portable entry points.

For a multi-framework experiment, read docs/FRAMEWORK_MATRIX.md and run `python3 -m spineharness.framework_matrix` inside the same WSL2 Ubuntu distribution. This new path is separate from Run-Harness.ps1's two-arm Jira workflow. An official SWE-bench resolved claim requires its Docker evaluator; Jira checks are local diagnostics. Keep hidden tests out of framework prompts.

For the historical two-arm Jira path, use the pinned Spine tools bundle from this archive. Configure real required public behavior checks before preparation; the native pipeline may refine against these checks within its recorded bounds. This is distinct from hidden post-run acceptance feedback. Never replace the native loop with a supervisor-authored repair. Report native outcome, required-check history, every model call and deterministic check time. Original checkout/Jira stay unchanged. New public check files belong in the common disposable baseline via behavior_files.
